Designed the schema/module/API contract for "apertura y cierre de caja" (2026-09-15), a small local-bookkeeping enhancement in the same category as `customers` — **not** a numbered roadmap phase, **not** a Dataico integration. Confirmed business rules came pre-settled from the human (see the handoff report delivered to the Architect's caller for the full design); key decisions worth remembering for consistency if this feature is extended later:

- **Table**: `cash_registers`. One row per calendar day, store-wide (not per user). `register_date DATE` with a **plain UNIQUE** index (not the partial/soft-delete-aware kind — this table has no soft delete, nothing FKs to it, no remove endpoint, same reasoning as `customers` having no remove()).
- **No status enum** — state is derived from `closed_at IS NULL`, matching how `dian_resolutions`/`invoices` avoid a redundant status column when a timestamp already implies it.
- **No generic `created_at`/`updated_at`** on this entity (doesn't extend `BaseEntity`) — `opened_at`/`opened_by_id` and `closed_at`/`closed_by_id` already timestamp the only two events this row ever has (open, then close once — no reopen flow per business rule). Adding a redundant generic pair would just duplicate `opened_at`.
- **Module placement: top-level `apps/api/src/cash-register/`**, sibling of `invoicing/`, NOT nested under `invoicing/`. Justification: mirrors `customers/`'s precedent exactly (local bookkeeping that touches invoicing but makes zero Dataico HTTP calls) — `invoicing/`'s subfolder tree is reserved for the 8 Dataico Postman-collection sub-domains per `ARCHITECTURE.md`, and cash register isn't one of them.
- **Gating integration**: `InvoicesService.create()` injects `CashRegisterService` and calls `assertOpenToday()` as the very first line (before the resolution lookup) — throws `BadRequestException` (not `ConflictException`) to match the exact sibling precedent already in that same method (`if (!resolution) throw new BadRequestException(...)` for the missing-DIAN-resolution gate). Gate applies ONLY to `POST /invoicing/invoices` — not to list/resend/refresh.
- **Circular dependency avoidance**: `InvoicesModule` needs `CashRegisterService` (for the gate) and `CashRegisterService` needs to SUM `invoices.total_amount` (for close()) — a genuine two-way need between peer modules, unlike the one-way `DataicoModule` hub pattern. Resolved by having `CashRegisterModule` do its own `TypeOrmModule.forFeature([Invoice])` and query the `Invoice` repository directly for the read-only aggregate, rather than importing `InvoicesModule`/injecting `InvoicesService` (which would cycle back). This is a deliberate, flagged exception to the codebase's usual "reach other domains through their service, not their repository" convention — justified only because it's a single trivial read-only SUM, not real business logic.
- **Timezone**: "today" must be computed in `America/Bogota` (fixed UTC-5, no DST), not server local time — Railway runs UTC, so a naive `new Date()` date-string would roll the register over at 7pm Bogotá time. Proposed a small `getStoreToday()` helper (`common/utils/`) using `toLocaleDateString('en-CA', { timeZone: 'America/Bogota' })`. Used consistently in `open()`, `close()`, `assertOpenToday()`, `getTodayStatus()`.
- **Total computation — CORRECTED from this design's original recommendation during implementation**: matched on `invoices.created_at` (TIMESTAMPTZ, converted to the Bogotá day range via `getStoreDayRangeUtc()`), **not** `issue_date` as originally proposed here. Reason found during implementation: the client's `InvoiceFormPage.todayIsoDate()` builds `issueDate` via `new Date().toISOString().slice(0,10)`, which is the **UTC** date, not the Bogotá-local date — near/after 7pm Bogotá time this already rolls to tomorrow's date. Matching the register total on `issue_date` would silently miscount invoices created late in the day. `created_at` is a server-set timestamp, immune to that client bug. If `issueDate`'s frontend computation is ever fixed to be timezone-correct, this choice should be revisited (either matcher would then be equally correct, but `created_at` remains the safer default). Also exposed as a live (unpersisted) `totalSoFar` field on the `GET /cash-register/today` response only while a register is open, computed via the same query, to back a close-confirmation modal showing the amount before the user commits — `CashRegisterResponseDto.totalAmount` itself stays `null` until actually closed (that field means "the persisted final total," never a live estimate).

Full endpoint list, DTO shapes, entity columns, and frontend contract (banner on the invoices list page, blocking screen on the create-invoice page, confirm-before-close modal) are in the design handoff itself, not repeated here.
